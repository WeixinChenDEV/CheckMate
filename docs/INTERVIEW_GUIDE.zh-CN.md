# CheckMate 项目与面试说明

本说明依据当前仓库代码及你确认的分工：前后端大部分由你独立完成。原有功能与本次辅助改进分开列出；面试时只描述自己理解并能演示的操作，不虚构用户量、商业收入或上线效果。

## 这个项目解决什么问题

旅行前容易漏带物品，多人出行时也容易不清楚谁负责带什么。CheckMate 是旅行打包清单 Web 应用，支持创建行程、勾选物品、复用模板和历史清单，并向好友开放只读或可编辑权限。天气和 AI 助手提供物品建议，用户确认后再加入清单。

它不是景点行程规划或订票平台。创建“行程”指的是带日期的打包清单，不是规划每天游览什么景点。代码中的 AI 提示词和输出过滤也限制了这类内容。

## 30 秒介绍

> CheckMate 是我主要独立完成前后端的旅行打包清单应用。我用 React 做界面，用 Flask 提供接口，用 MySQL 保存账号和清单。用户可以创建清单、分享给好友，并设置查看或编辑权限。我还接入了天气和语言模型接口，让用户获取物品建议、选择需要的物品后加入清单。项目重点是把这些功能串成一个能保存和复用的打包流程。

## 面试官常问什么

### 你具体负责哪些部分？

> 我主要独立完成了前后端实现，包括页面与接口连接、清单的保存和更新，以及天气和 AI 功能的接入。

接着选一个你确实熟悉的模块讲细节。不要把团队其他人的贡献也算进来。

### 前后端怎么连接？

> React 通过 fetch 请求 Flask 的 API。后端校验登录身份，读取或保存数据库，再返回 JSON。前端拿到结果后更新页面。例如创建清单时，前端提交名称、物品和日期，后端保存成功后，前端刷新清单列表。

### 为什么需要数据库？

> 清单需要在刷新页面和下次登录后仍然存在，而且共享清单需要双方看到同一份保存的数据，所以不能只放在页面状态里。

### 共享权限怎么实现？

> 后端保存清单拥有者、被分享用户和是否允许编辑。只读用户不能更新清单；允许编辑的用户可以更新物品，但不能修改拥有者的清单设置。界面会限制操作，后端也会检查权限。

共享是基于保存后读取数据，不要将它描述成 WebSocket 实时协作或自动解决并发冲突。

### AI 功能是你训练模型吗？

> 我使用现有语言模型 API。我负责组织请求、处理返回结果，并把物品建议接到清单流程里，没有训练模型。

### AI 建议如何变成清单？

> 后端请求模型返回打包建议。前端从物品列表中提取文本，区分必带和普通物品，再由用户勾选确认。用户可以用这些物品新建行程，或追加到可编辑的现有清单。追加时还会检查重复物品。

模型服务没有配置或请求失败时，后端已有规则式建议作为回退；这部分不能说成仍然在使用真实 AI。当前解析仍依赖文本格式，后续可考虑结构化 JSON 输出。

### 天气怎么影响清单？

> 后端从天气接口获取数据，前端依据温度、降雨或紫外线等条件生成携带建议。例如雨天提示带雨伞。天气建议与 AI 对话是两个相关功能，不能声称每次 AI 请求都会自动带入实时天气。

首页天气使用定位或请求位置，不应描述为每个行程自动按目的地查询完整天气。

### 做过什么改进？

以下是本次辅助完善的实际改动，理解代码后可以按真实过程解释：

- AI 导入原先主要识别短横线物品列表；现在也能处理 Markdown 标题、编号和复选框，去重并保留必带优先级，排除提示和追问。
- 新建行程增加选填返程时间，并将它传给后端保存；日期输入的最早时间使用本地时间，修正直接使用 UTC 字符串的问题。
- 天气接口拒绝不完整、非数字和越界坐标，避免错误输入悄悄查询默认城市。
- 天气全部服务失败时返回未知温度，页面不再显示固定 22°C，也不根据这个假温度推荐衣物。
- 增加前后端回归测试、GitHub Actions 检查及无需 MySQL 服务的本地演示配置。

### 项目还有什么不足？

> 目前是课程和作品集规模的应用。共享清单更新仍以保存和刷新为主，没有实时同步或并发编辑冲突处理。AI 文本格式仍可能变化，所以需要用户确认建议。另外，后端逻辑比较集中，后续可以按账号、清单、天气和助手拆分模块。

这是现有实现的具体限制，不需要声称已经完成这些后续改进。

## 演示顺序

1. 注册账号，创建一张含出发与返程时间的清单。
2. 添加必带和普通物品，保存后刷新，确认仍然存在。
3. 用第二个账号接受好友请求，演示只读和可编辑权限。
4. 打开助手，生成物品建议，选择部分物品导入清单。
5. 查看天气建议；没有网络时说明未知状态与回退行为。

本次自动化验证使用隔离的 SQLite 和模拟外部服务。真实天气、付费 AI 和云部署效果需要使用你自己的配置单独演示。
